# Balancer — система анализа изменений СПР

Первый этап хакатона. FastAPI загружает пары ответов и ставит запуски в очередь MySQL 8.4. Отдельный Python worker нормализует ответы, сравнивает атрибуты, запускает проверки и сохраняет факты для будущего отчёта.

## Структура

| Каталог | Назначение |
| --- | --- |
| `backend/` | API, загрузка ZIP, MySQL и MartAPI для проверок |
| `procedures/` | Встроенные заменяемые процедуры нормализации и сравнения |
| `worker/` | Очередь, пакетная запись, проверки и агрегация |
| `migrations/` | Начальная схема MySQL |
| `plugins/` | Точка подключения доверенных Python-файлов |
| `tests/` | Сверка с примерами организаторов и сквозная проверка API |
| `frontend/` | Место для React, TypeScript и Tailwind CSS |

## Запуск

Нужны Docker с Compose v2 и Python 3.12 для локальных проверок. Из внешнего архива откройте `ПАКЕТ/ЗАДАНИЕ.zip`. Сохраните этот ZIP как `.organizer/task.zip` и распакуйте его в `.organizer/`, чтобы появился каталог `.organizer/ЗАДАНИЕ/`. Для проверки используются только материалы из пакета участника.

1. Скопируйте `.env.example` в `.env` и задайте два отдельных локальных пароля MySQL. Для подключения пяти проверок организаторов задайте `PLUGINS_DIR=./.organizer/ЗАДАНИЕ/checks`. При стандартном `PLUGINS_DIR=./plugins` можно поместить доверенные файлы туда.
2. Выполните `docker compose up -d --build`. На Windows, если Docker использует контекст `desktop-linux`, команда выглядит как `docker --context desktop-linux compose up -d --build`. Миграция применяется при первой инициализации тома.
3. Откройте [Swagger UI](http://127.0.0.1:8000/docs). Чтобы прогнать полный датасет автоматически, выполните команды ниже из корня проекта.

```sh
python -m unittest discover -s tests -v
python -m tests.smoke .organizer/task.zip
```

Переменная `ORGANIZER_DIR` переопределяет расположение распакованных материалов для модульных тестов. Для другого порта укажите `--url` при запуске smoke-теста.

## API

| Метод | Действие |
| --- | --- |
| `POST /datasets` | Поле multipart `file` с ZIP, содержащим одно дерево `RESULTS/BEFORE_MASTER` и `RESULTS/AFTER_BETA`. Имена JSON задают идентификаторы заявок. |
| `POST /runs` | Создать конфигурацию и запуск. Минимальное тело `{"dataset_id":1}`. |
| `POST /runs/{id}/start` | Поставить запуск в очередь. Повторный вызов не дублирует задачу. |
| `GET /runs/{id}` | Получить статус, этап, число обработанных заявок, ошибку или итоговые счётчики. |
| `GET /runs/{id}/results` | Получить строки сравнения. После завершения запуска поддерживает `app_id`, `path`, `array_key`, `change_type`, `only_differences`, `limit` и `offset`. |
| `GET /runs/{id}/checks` | Получить строки единого отчёта проверок с `APP_IDS`. |
| `GET /runs/{id}/facts` | Получить агрегированные факты с `CNT` заявок на группу. |
| `GET /runs/{id}/logs` | Получить журнал этапов и ошибки. |

Worker обрабатывает один запуск за раз, записывает атрибуты и прогресс пакетами и восстанавливает прерванный запуск с начала при перезапуске. После ошибки обработки можно создать новый запуск с исправленной конфигурацией. API доступен локально. В схеме есть пользователи и ссылки на владельцев, но на текущем этапе API создаёт записи без владельца и доступ к данным общий. Поле `users.password_hash` зарезервировано для хешей.

## Процедуры и правила

Поля запуска `normalizer` и `comparator` принимают `builtin` или имя файла из каталога плагинов без расширения. Worker импортирует эти файлы при запуске задачи. Каталог монтируется только для чтения. Размещайте в нём код, которому доверяете, поскольку он выполняется с правами worker.

- Модуль нормализации экспортирует `normalize(app_id, source, document, params)` и `segments(app_id, before, after, params)`. Первая функция возвращает строки с колонками `APP_ID`, `SOURCE`, `PATH`, `PREFIX`, `CLASS`, `SUFFIX`, `KEY`, `ARRAY_KEY`, `VALUE`, `ADJUSTED_VALUE`. Вторая возвращает один словарь разрезов по схеме организаторов.
- Модуль сравнения экспортирует `compare(before, after, params)` и возвращает строки витрины сравнения. Встроенный вариант использует ключ `(APP_ID, PATH, ARRAY_KEY)` и сравнивает `VALUE`.
- Проверка экспортирует `CHECK` по контракту организаторов. Поле запуска `checks` задаёт соответствие между именем файла без расширения и параметрами. При отсутствии поля выбираются все файлы `check_*.py`, при `"checks":{}` проверки пропускаются.
- `normalize_params.ignore` заменяет список исключений. По умолчанию исключаются `appData.request_id` и `appData.createDateTime`. Оба справочника включены. `normalize_params.arrays` задаёт для пути список ключевых полей, режим `value` или `index`. `normalize_params.buckets` задаёт интервалы `[нижняя_граница, верхняя_граница, метка]` для каждого пути. Без интервала бакет совпадает со значением.
- Вложенные ключи массивов соединяются через `|`, части составного ключа через `:`, индексы начинаются с нуля. Значение JSON `null` представлено строкой `NULL`, а отсутствие атрибута в сравнении — SQL NULL. Поэтому переход `null → false` считается изменением значения.
- `PRODUCTS` содержит объединение идентификаторов продуктов обоих срезов. Разрезы порога и модели берутся для продукта первого оффера, а при его отсутствии из прогона продукта с минимальным идентификатором в лексикографическом порядке. `PARTNER_TYPE` и `ROUTING_METHOD` относятся к AFTER.

React-интерфейс, разграничение доступа, интерактивный редактор и отчёты с переходом от агрегата к заявке относятся к следующим этапам.
